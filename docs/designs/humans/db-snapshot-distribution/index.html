数据库快照分发 validated

验证于 2026-05-15 · 由一次 /spike 而来 · 完整细节见 agent 设计文档

这是什么

把本机已经跑完 Day-0 全量 bootstrap 的 5 个 SQLite（合计 3.5 GB）打包成 GitHub Release 附件， 让朋友新机器在 10 分钟内拿到完整数据集，不必再花 10 小时跑一遍 ETL。

怎么工作

核心想法：把 prices.db 按年切成 4 个文件 + 一个 core 包。历史分片发完不再变，只有"hot"那档每周重发。

分片rawzst -19重发
prices_2005-2015.db.zst924 MB~138 MB一次性
prices_2016-2020.db.zst812 MB~121 MB一次性
prices_2021-2024.db.zst975 MB~145 MB一次性
prices_2025-2026.db.zst360 MB~54 MB每周（hot）
core.tar.zst（entities + holdings + wd_cache）325 MB~50 MB跟随 hot
合计3.5 GB~510 MB—
朋友首次拉数据 git clone … → uv sync → python scripts/migrate.py → python run.py snapshot pull（下载 5 个 zst，本地解压 + ATTACH 合并回单个 prices.db） → python run.py up。整套流程 100 Mbps 上约 5-8 分钟。

之后每周（见姊妹设计 ETL 周度刷新）GitHub Actions 自动重打 hot 那 ~54 MB，朋友本地 cron 拉新 hot 即可跟上数据。

关键点：运行时代码完全没动。 ATTACH 只在一次性的打包 / 合并脚本里用， 跑完即关；线上服务依旧是单个 prices.db，守住 CLAUDE.md "5 库不 ATTACH" 的约定。

决策与原因

  • prices.db 全保留，不瘦身。代码现在只查 SELECT close … LIMIT 1，理论可瘦 99% 至 <10 MB；但为未来 K 线视图保留扩展空间。
  • 按年分片，不是按市场或哈希。年片是唯一支持"历史不变 + 只重传 hot"的策略，把每周分发量从 ~510 MB 压到 ~54 MB。
  • zstd -19 而非 gzip。同样 74 MB 输入，gzip 出 16.9 MB，zstd 出 11 MB（再省 30%）。压缩时间 5s vs 26s 都在容忍范围。
  • GitHub Release 当托管，不要对象存储。仓库已有、免费、私有也支持、单文件 2 GB 上限够用。
  • meta.db 不分发。etl_progress / dead_letter 是本机私有进度，新用户从空开始。

验证过什么

  • 切 2026 年片：810k 行 11.6 秒切出 74 MB raw → zstd -19 11 MB（14.9% 压缩率）。
  • 合并链路：zstd -d + ATTACH + INSERT OR REPLACE 把 810k 行合进空 db 用 0.8 秒。查询结果（sh600004 close ≤ 2026-06-01 = 8.52）和源 db 字字一致。
  • 外推全分发：4 个年片 + core ≈ 510 MB，每个文件远小于 GitHub Release 单文件 2 GB 上限。

遗留风险

  • 历史分片"永不变"假设依赖 AKShare 不修复历史数据；理论上偶有 ~5 万行少量修正，需要时重发也只是 138 MB 上传 30 秒。
  • GitHub CDN 国内速度不稳；510 MB 首次下载 1-7 分钟内可接受。真痛了再加七牛 / R2 镜像。
  • 2027 年 hot 跨年滚动需要本人手动跑一次 python run.py snapshot roll-year；GH Actions 不感知跨年。
